# 3D Scroll Experience — `/experience`

A scroll-driven tour of BVCITS built with the sticky-canvas frame-sequence
technique (the same one behind Apple's product pages and Igloo-style agency
sites). Route: [`src/app/experience/page.tsx`](../src/app/experience/page.tsx).

## The mental model

The "3D" is **not** runtime WebGL. It is a pre-rendered image sequence that a
`<canvas>` scrubs through based on scroll position:

```
<section class="scroll-animation">        ← 400vh, creates the scroll distance
  <div class="sticky top-0 h-screen">     ← pins to the viewport
    <canvas />                            ← draws frame N for scroll progress N/total
```

Everything else is polish: Lenis smooth scroll, neumorphic surfaces, CSS-transition
annotation cards.

## Where the frames come from

Normally you render these in Blender or Cinema 4D. This project has no 3D
assets, so both sequences are generated by a **software 3D renderer written for
this repo** — no new dependencies, `sharp` (already present via Next.js) does the
JPEG encoding.

```bash
npm run frames                                  # both sequences, tuned defaults
node scripts/render-frames.mjs core             # just the hero
node scripts/render-frames.mjs all --width=1920 --height=1080 --quality=80
```

| File | Role |
|---|---|
| `scripts/render-frames.mjs` | CLI, encoding, manifest generation |
| `scripts/lib/render3d.mjs` | Framebuffer, additive splat rasteriser, bloom, tone mapping |
| `scripts/lib/geometry.mjs` | Icosphere subdivision, orbit rings, corridor gates |
| `scripts/lib/scenes.mjs` | The two scenes and their scroll timelines |

Rendering is deterministic (seeded PRNG), so the same command always produces
byte-identical frames.

### Output budget

Current defaults are 1280×720 @ JPEG q66:

| Sequence | Frames | Size |
|---|---|---|
| `core` | 80 | ~3.6 MB |
| `corridor` | 64 | ~2.0 MB |

The hero sequence loads on first paint. The corridor is deferred until the
section is within ~1.5 viewports (`useNearViewport`), so it never competes with
the hero.

### Swapping in real Blender frames

The engine does not care where the JPGs come from. To replace them:

1. Export an image sequence named `frame_0001.jpg`, `frame_0002.jpg`, …
2. Drop it in `public/frames/` (or `public/tunnel-frames/`).
3. Update the counts in `src/lib/frame-manifest.ts`.

`frame-manifest.ts` is **generated** by the render script from what is actually
on disk — that is what stops `FRAME_COUNT` drifting from the real sequence, the
classic cause of a blank final frame. If you hand-place frames, edit it manually
or re-run the script.

## The engine

[`src/components/scroll3d/useScrollCanvas.ts`](../src/components/scroll3d/useScrollCanvas.ts)
holds three hooks the sections compose:

- **`useFramePreloader`** — loads the sequence, reports real progress, and settles
  on `onerror` so one missing frame can never hang the loader.
- **`useCanvasRenderer`** — sizes the canvas to `devicePixelRatio` and pre-scales
  the context so all draw math stays in CSS pixels. Cover-fit like
  `object-fit: cover`, with a 1.3× zoom under 768px. Repeat frames are skipped.
- **`useScrollProgress`** — passive scroll listener, RAF-throttled behind a
  ticking ref, emitting 0..1 progress.

### The rule that matters

Nothing that changes on every scroll tick goes through React state.

- Canvas pixels → `drawImage` via ref
- Hero/intro text opacity → `ref.current.style.opacity`, and only when the value
  moves more than 0.008
- Annotation visibility → `setState` only when the visible **set** changes
  (`diffVisibleZones` returns `null` otherwise)
- Card show/hide → CSS transitions, not Framer Motion

## Performance checklist

| Check | Status |
|---|---|
| Frames preload behind a real progress bar | Yes — `FrameLoader` |
| RAF + ticking ref on scroll | Yes |
| Canvas scaled for `devicePixelRatio` | Yes — verified 1280×720 @ DPR 1 |
| Canvas updates bypass React | Yes |
| Visible-set `setState` only on change | Yes |
| Passive scroll listeners | Yes |
| Lenis Safari-safe config | Yes — `lerp: 0.1`, `syncTouch: false` on Apple WebKit |
| Mobile 1.3× zoom + shorter sections | Yes — 400vh → 350vh → 300vh |
| Production build tested | Yes — 260 pages, `/experience` 184 kB First Load JS |
| Reduced motion | Sections collapse to 100vh, one static frame drawn, no scrubbing |

Not yet measured: Lighthouse scores, and real iOS Safari. Both need a device or a
deployed URL.

## Promoting it to the home page

`/experience` is standalone and changes nothing else. To make it the landing
page, swap the body of `src/app/page.tsx` for the five components in
`src/app/experience/page.tsx` (or re-export it).
